# Architecture

## Решение по платформе

Для MVP используется единый managed-контур:

- `Supabase` для `Postgres`, `Storage`, `Edge Functions`, `pg_cron`;
- `Telegram` как основной пользовательский интерфейс;
- `Notion` как внешний read-model/dashboard;
- `OpenRouter` как основной AI-провайдер;
- `Codex` как среда проектирования и реализации.

`Vercel` не используется в MVP, так как веб-интерфейс исключён, а для backend-задач он добавит лишний инфраструктурный слой без заметной выгоды.

## Уточнения относительно исходного документа

Исходный документ содержит следы старой архитектуры. Для текущей версии проекта принимаются такие решения:

- везде вместо `Claude Code` используется `Codex`;
- везде вместо `Claude API` и `Anthropic API` используется `OpenRouter`;
- локальный `Mac`-контур удаляется из архитектуры MVP;
- `Apple Calendar` исключается из MVP;
- поле окружения `ANTHROPIC_API_KEY` заменяется на `OPENROUTER_API_KEY`.

## Контуры системы

### 1. Входящий контур

`Telegram Bot` отправляет обновления в `Supabase Edge Function` `telegram-webhook`.

Функция должна:

- проверять секрет webhook;
- обрабатывать повторные доставки идемпотентно;
- сохранять неизменяемый оригинал входящего объекта;
- складывать вложения в `Supabase Storage`;
- создавать запись в очереди обработки;
- сразу отвечать пользователю коротким подтверждением.

### 2. Контур обработки

`process-inbox` выполняется фоново и обрабатывает записи со статусом `pending`.

Пайплайн:

1. взять запись в работу через lease/lock;
2. при необходимости скачать вложение;
3. выполнить `STT` или `OCR`;
4. вызвать `OpenRouter`;
5. сохранить summary, classification, links, drafts и confidence;
6. при необходимости отправить результат или уточнение в Telegram;
7. перевести запись в `processed` или `failed`.

## Данные

Минимальные доменные сущности для старта:

- `inbox_items`
- `inbox_attachments`
- `processing_jobs`
- `item_analysis`
- `proposed_entities`
- `audit_log`
- `outbound_messages`
- `scheduler_runs`

Ключевые инварианты:

- оригинал не изменяется после сохранения;
- AI-результаты живут отдельно от оригинала;
- каждое изменение имеет `created_at`, `updated_at`, `author`, `status`, `revision`;
- критичные действия пишутся в `audit_log`;
- повторный `Telegram update` не создаёт дубль.

## Интеграции

### OpenRouter

Интеграция идёт через отдельный адаптер, чтобы доменная логика не зависела от конкретного SDK или формата вызова.

Стартовая рабочая конфигурация:

- `OPENROUTER_BASE_URL=https://openrouter.ai/api/v1`
- `OPENROUTER_MODEL=openai/gpt-4.1-mini`
- ограничение `max_tokens` задаётся в адаптере для контроля стоимости и предсказуемости ответа

Рекомендуемый контракт адаптера:

- `classifyInboxItem(input)`
- `summarizeDay(input)`
- `prepareWeeklyReview(input)`
- `extractFinanceOperations(input)`

### Notion

`Notion` не хранит мастер-копию данных. Он получает только подтверждённые или явно предназначенные для показа записи.

Синхронизация должна быть:

- идемпотентной;
- ориентированной на upsert;
- восстанавливаемой после сбоя;
- не блокирующей основной ingestion pipeline.

## Планировщик

Для фоновых запусков используется `pg_cron`.

Стартовые расписания:

- `22:00` ежедневно для `evening-dialog`;
- воскресенье вечером для `weekly-review`.

Часовой пояс должен управляться конфигурацией через `TIMEZONE`, а не быть зашитым в код.

## Безопасность

- все вызовы только по `TLS`;
- секреты не хранятся в репозитории;
- `service role key` используется только внутри server-side компонентов;
- в логах нельзя хранить токены и чувствительные пользовательские тексты целиком;
- рабочая информация должна быть обезличенной.

## Хостинг

Базовый вариант:

- один проект `Supabase`;
- один Git-репозиторий;
- деплой Edge Functions через Supabase CLI или CI.

Резервный вариант на будущее:

Если длинные аудио, тяжёлый OCR или большие PDF перестанут укладываться в ограничения Edge Functions, тяжёлый шаг переносится в отдельный always-on worker на `Railway` или `Render`, но API-контракт и хранилище остаются прежними.
